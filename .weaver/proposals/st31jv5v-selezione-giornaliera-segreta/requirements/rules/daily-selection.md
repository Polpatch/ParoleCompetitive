# Secret daily selection rules

## daily-word

- Use the Gregorian calendar day in IANA time zone Europe/Rome, including daylight-saving changes, independent of the device's chosen time zone. Every compatible updated client uses the same fixed assignment for that date and vocabulary.
- Secret selection starts on the explicit date 2026-11-08, taking effect when the authorized implementation is released. Dates before it keep their v1 assignments. This replaces, rather than supplements, the planned v2 activation on 2026-11-09. Never derive activation from build time or opening time.
- On first reconciliation, withdraw only the activation date's superseded public-calendar challenge and its result, even if won, lost, expired or discovered after activation. Withdrawal is not a loss. Preserve earlier games and preferences. If that date is current, offer a separate fresh HMAC game only after acquiring its valid selection; otherwise create no replacement game for the past date. Repeated open, reload, rebuild and competing tabs cannot reset the HMAC game or count another withdrawal. The next day cannot trigger the abandoned vocabulary cutover.
- The complete canonical allowed-guess set is also the eligible-solution set. There is no smaller solution subset or change to vocabulary admission, hard mode, score, autocomplete, reveal, statistics or letter-free sharing. A published static daily selection is allowed; no runtime source scraping, application API or official Wordle affiliation is introduced.
- Reconcile outstanding withdrawal before ordinary expiry on open, visibility return and the visible Rome day boundary. Expire preceding unfinished games at their actual boundary even if today's data is unavailable. Do not invent games or losses for intervening unplayed days; an unavailable current challenge has no attempts, solving time, locked per-game choice, score or outcome.
- Acquire the current selection once on opening, visible return, a visible day boundary or explicit Riprova, unless its valid assignment is already retained. Concurrent triggers may share one pending acquisition. No timed retries, backoff, periodic polling or automatic repeated fetching after failure. An explicit retry starts one acquisition; duplicate clicks while acquiring do not start parallel draws or games.
- A retained valid current-day assignment remains playable without network until that Rome day ends. No earlier day's record can stand in for today. Missing, failed, malformed or incompatible data with no retained current assignment leaves the challenge unavailable; no public-calendar fallback or local draw is permitted. Recheck the date and request identity when an acquisition completes; obsolete completions cannot activate a past day or overwrite a newer request.
- Compatible clients must agree on date, schema, vocabulary and challenge identity. A new client rejects incompatible data and offers update guidance without deleting saved data. Cached pre-cutover clients cannot be remotely revoked on a static site; document that they may keep playing their old public schedule and are outside the common-challenge guarantee.

## daily-publication

- For a previously unfixed current Rome date, decode `PAROLE_DAILY_HMAC_KEY` from exactly 64 hexadecimal digits to 32 cryptographically random bytes. HMAC-SHA256 uses those bytes as key and the canonical date's UTF-8 bytes, without a newline, as its entire message. Interpret all 32 digest bytes as one unsigned big-endian integer; the zero-based solution index is that integer modulo the canonical vocabulary length. Do not truncate to a JavaScript Number, add a numeric salt or mix in build randomness. No vocabulary identifier is appended to the HMAC message.
- The same key, date and vocabulary ordering always yield the same selection. Independent modulo selection may repeat past words; there is no permutation-cycle or no-repeat promise. The key and ordering remain stable between runs, and the first durable record takes precedence over any later calculation.
- One scheduled request runs at `00:07` with IANA timezone `Europe/Rome`. Use the actual Rome date at generation, not the nominal scheduled date; never prepublish tomorrow or backfill unfixed missed days. Midnight availability is not guaranteed. The schedule avoids the DST transition hour, while every run still derives and validates the date explicitly.
- Trusted main releases and authorized `workflow_dispatch` recovery may request publication of the current day. They reuse an existing record, including when the secret is absent and no new assignment is needed. Missing or malformed key material blocks creating an absent record, with no random fallback, regeneration or misleading success.
- Publication delay or failure leaves clients honestly waiting; no alternative selection and no automatic retry policy is added. Re-running after a durable write but failed Pages deployment republishes the same record. A run crossing a Rome boundary cannot promote its preceding day's record as current.
- Key loss or proposed rotation stops creation of new assignments until the developer authorizes provisioning or an explicitly dated prospective replacement period. Already fixed days remain unchanged and can be republished without the old key. Never automatically create a new key when a run cannot read the existing one.
