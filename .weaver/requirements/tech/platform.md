# Static platform

## General
- TypeScript with strict type checking, Vite, DOM APIs and CSS; no React or other UI framework. Keep pure word evaluation, score calculation and day selection separate from DOM effects without introducing a second state store or unnecessary abstractions.
- Use npm and a committed lockfile. Use Vitest for deterministic rule tests and Playwright for an actual built-site browser smoke. Choose mutually compatible stable versions and record the Node.js LTS version used by both local tooling and CI.
- Initialize Git in this folder and automatically create a public GitHub repository named ParoleCompetitive under the authenticated GitHub CLI account. Install GitHub CLI if absent and require authorized authentication rather than fake credentials. The initial checkout is not a Git repository and gh is absent from PATH.
- Do not overwrite an existing remote repository or an unexpected existing checkout. A name collision, missing authorized GitHub identity, missing permissions or unavailable Pages provisioning must produce an explicit actionable blocker, not a made-up repository, URL or successful deployment claim.
- Main branch is main. Commit the project and lockfile and connect origin to the actual created repository. Keep generated output, secrets, node_modules and local agent runtime state out of version control; retain the project's intended Weaver definitions according to its workflow.
- GitHub Actions runs on pull requests and main pushes: install from lockfile, type-check, deterministic tests, production build, built-site browser smoke. Deploy the verified build automatically only from main with official Pages artifact/deploy actions, GitHub environment and least-privilege permissions. No third-party deployment token is needed. The daily-selection secret is required only by trusted generation, never by PR verification or the frontend build.
- Configure the Pages project-site base path for ParoleCompetitive, including assets and any result links. Verify by serving the production build under that prefix; no server-side route rewrites. Configure the repository's Pages build source and environment as part of provisioning when permissions allow.
- No Terraform, Bicep, serverless functions, database service or other cloud infrastructure. GitHub workflow files are the only release automation infrastructure needed.
- Maintain English project documentation for local prerequisites, install/run/check/build, source list provenance and license caveat, secret daily selection and preserved historical schedule, exact score, hard/standard behavior, browser storage limitations, native-sharing fallback, GitHub provisioning and Pages release. Include a short changelog for the delivered initial application. Document executable verification commands and accurately describe the coverage present in the checked-in test suite.

## daily-publication

- Extend the existing GitHub Actions/official Pages path with trusted default-branch `schedule` (`cron: '7 0 * * *'`, `timezone: Europe/Rome`) and authorized main-only `workflow_dispatch`, retaining pull-request and main-push verification. Keep strict TypeScript, npm lockfile, Node 24 LTS, Vitest, production build and built-site Playwright smoke. No new cloud service, application backend, PWA or third-party deployment token.
- One shared concurrency group must serialize the whole trusted publication path, from source/record acquisition through final Pages deployment, with no cancellation of an in-progress publisher. Do not lock only the final deployment job. GitHub may replace pending runs; do not promise FIFO or guaranteed delivery. PR verification has no privileged publishing path.
- After obtaining the publisher slot, choose the latest trusted main revision, pin it for all verification/build steps, and record it in deployment metadata. Before promotion, confirm main still matches that verified revision and the Rome date still matches the candidate; if either changed, stop without promotion. A later authorized run starts with current main; do not add automatic retry loops. A code release must merge the current fixed record into its complete artifact rather than replacing it with a bundled schedule or deleting the data path.
- Restrict `contents: write` to the trusted durable-record job and `pages: write` plus `id-token: write` to deployment using the existing github-pages environment. Default permissions remain read-only. The data job writes the daily-data branch without executing code from it; branch updates cannot recursively trigger a main release. A pre-existing unexpected branch or record must be validated, not overwritten.
- The generator uses Node.js built-in crypto and the canonical local vocabulary. Only its trusted main generation step receives PAROLE_DAILY_HMAC_KEY. Do not pass it to npm install, test, browser smoke, Vite build, pull_request or pull_request_target code. Public-record validation and republishing need no secret; generation with a production key must not run untrusted dependencies or PR scripts.
- In subsequent authorized implementation, the assistant may generate 32 bytes with a cryptographically secure generator and set PAROLE_DAILY_HMAC_KEY via GitHub CLI protected standard input using authorized access. Never print or request its value in Chat, persist it in versioned files, expose it in arguments, frontend environment variables, logs or artifacts, or regenerate an existing secret. If authentication, repository-secret write, branch-write or Pages-environment permission is missing, identify that precise authorization for the developer; do not request that the key be pasted into Chat.
- Assemble the full static artifact with only daily/current.json for the current day. Resolve the client request from Vite's configured Pages base URL, not a domain-root path. Fetch with browser cache bypass (`cache: 'no-store'`); GitHub Pages header control is not assumed, so validate date and vocabulary even after a successful HTTP response. No service worker or persistent HTTP-cache correctness assumption.

Describe exact HMAC/identity bytes, activation 2026-11-08, removal of the abandoned v2 cutover, secure provisioning, immutable branch, schedule/timezone, manual recovery, code/data concurrency, key loss/rotation, repeats, exposed current answer, old-client limits, delayed/failed publication and same-day-only offline play. Keep executable check commands and coverage claims accurate.
