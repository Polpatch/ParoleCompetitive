# ParoleCompetitive

A browser-based daily Italian word puzzle. This is not an official dictionary or an official Wordle product. All game data stays in the browser; there is no account, backend, online leaderboard, analytics, or cross-device sync.

Play online: https://polpatch.github.io/ParoleCompetitive/

## Development

Use Node.js 24 LTS (the exact development and CI version is in `.nvmrc`) and npm. From the project root:

```sh
npm ci
npm run dev
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run smoke
```

The Playwright smoke runs against the production build through a dedicated Vite preview at `/ParoleCompetitive/`; run the build first. It refuses to reuse an existing server. If port 4173 is occupied, set `PLAYWRIGHT_PORT` to a free port when running the smoke. `npm run preview` serves the build locally. The Vite base path is the GitHub Pages project-site prefix; assets and links must retain it.

## Daily challenge and rules

The day is the Gregorian calendar date in `Europe/Rome`, including daylight saving time, regardless of the device time zone. Before 8 November 2026, the frozen v1 schedule uses 2026-01-01 as its epoch; the integer calendar-day difference, modulo the ordered v1 list using a nonnegative remainder, selects its solution. On release, secret selection uses 8 November 2026 as its fixed activation boundary and replaces that date's public challenge once, including completed games or a replacement discovered later, without an additional loss. Earlier dates and preferences remain intact. The proposed 9 November v2 cutover was abandoned and causes no second reset. Compatible clients fetch the current selection and wait honestly if it is unavailable or incompatible; waiting creates no game or result, and an explicit retry makes one acquisition without polling. Earlier unfinished games still expire under the existing rules. See [word data](data/README.md) for vocabulary provenance, vocabulary identity and the exact publication algorithm.

After acquiring the static assets and a valid selection for today, that day's game needs no network and can reuse the retained selection if acquisition later fails. This does not promise a cold offline opening or knowledge of future challenges. The same challenge is guaranteed to updated compatible clients; a static site cannot revoke old copies of the public calendar.

Later public-calendar games already saved by an older client are retained separately from acquired challenges on the same date. Their results remain in local statistics, and unfinished games expire at the actual Rome day boundary even when today's selection is unavailable. Updated clients reject obsolete public-calendar progress.

Each game allows six five-letter ASCII guesses. Exact matches consume letters first; misplaced matches consume remaining occurrences left to right. The keyboard retains the strongest evidence, and letters shown to be entirely absent cannot be used again. In hard mode, greens remain fixed, yellow letters must occur outside their previously excluded positions, and each revealed letter must appear at least as many times as the highest positive count in any one prior row. A game may be downgraded from hard to standard after starting, but it cannot switch back and loses the hard bonus; before the first accepted guess either choice is allowed.
The Italian interface includes an on-screen keyboard and physical keyboard input, a rules guide, settings and local statistics. The keyboard uses three fixed QWERTY rows, with a backspace symbol before the last row of letters and an enter symbol after it; their accessible names remain Cancella and Invio. Embedded keys use static pressed feedback, one immediate action, a first repeat after 1000 ms and subsequent repeats every 150 ms. Moving away or opening navigation cancels the hold and releases pointer capture. A submitted row reveals left to right with overlapping one-second flips, starting 0.3 seconds apart; further input waits for the last flip. Reduced-motion settings reveal feedback and unlock ongoing games immediately. Difficulty and spoiler-free sharing can be selected in Settings; spoiler-free changes only later shares.
The prominent title has a short underline. Its circular menu button expands into a contrasting vertical capsule with minimal SVG settings, guide and statistics icons, while the hamburger becomes a centered X. The menu overlays the game without moving it, blocks game input while open, and closes with its button, Escape or an outside press. Choosing an action opens one dialog; closing that dialog with its X, Escape or the backdrop returns focus to the menu button. The game clock continues during navigation. Settings offer system, light and dark appearance. A newly completed game opens its statistics after the final reveal; opening Statistics later also shows the fixed score and solving duration (m:ss, or h:mm:ss from one hour), measured between the first and final accepted guesses. Sharing is available in the Statistics footer after the result is revealed.
The complete live board and its small right-aligned date are centered above the three-row keyboard, which stays at the bottom of the visible viewport above the bottom safe area. On shorter screens, with enlarged text or persistent warnings, the upper game area scrolls independently; if usable controls cannot fit above the keyboard, the whole page scrolls. Brief feedback appears as one soft, rounded top-center toast, with a small upper-right SVG close icon and an accessible hit area. It stays for four seconds of active viewing, pausing on hover or keyboard focus, then fades out over 200 ms; manual dismissal uses the same fade and reduced motion closes immediately. An open dialog contains the sole toast near its top center. Feedback never changes the board layout; acquisition and storage warnings remain persistent. The guide explains the browser-local data limitations. The page requests suppression of voluntary double-tap and pinch zoom where browsers permit it; browser and operating-system magnification and user overrides remain outside its control. No physical touch device was available, so native gesture suppression was not verified on hardware.
The Statistiche tab shows cumulative points, win/loss cards and a six-column histogram of wins by attempt. The Storico tab offers read-only local match history; expanding a match reveals its saved guesses, feedback and fixed duration on this device. Historical grids show only accepted attempts, without unused rows or drafts; the playing board and shared results still use six rows. History is independent of spoiler-free sharing and contains only retained, concluded games.

Appearance defaults to following the device and responds to system changes immediately; light and dark override the device until system is selected again. The selected preference, rather than the resolved color scheme, is stored with the local session and older sessions default to system. If storage is unavailable, appearance still works for the current page but cannot be promised after a reload.

The Settings dialog provides an accessible Autocomplete control, off by default. Enable it before the first accepted guess; rejected submissions do not lock the choice or change draft letters. Once play starts, the control is disabled and explains that neither the current game nor the future preference can be changed until the game ends. Preferences are saved with the game session and reconciled across tabs. A completed game retains its choice and score when the future preference changes; new days and replacement challenges use that future preference. After a wrong guess has finished revealing, all previously discovered green positions are fixed in the next draft; typing and deletion skip them. Saved games preserve the positional draft and older saves remain compatible.

For each accepted row let G and Y be its green and yellow counts; compare each with the immediately preceding row, initially zero: ΔG=max(0,G−previous G), ΔY=max(0,Y−previous Y). If either delta is positive, set consecutive stagnation s to zero; otherwise increment s from zero. The base is `B = 1000 + Σ(100·ΔG + 40·ΔY − 50·max(0,s−1))`. For a win in n guesses, with elapsed seconds t from the first accepted submission to the terminal submission, `score = round(max(0,B)/(n·(1+t/60))·m·a)`, where m is 1.10 only for a game started hard and never downgraded, otherwise 1, and a is 0.98 when autocomplete was enabled at the first accepted guess, otherwise 1. Both factors are applied before the single final rounding. Losses and started expiries score zero. Time includes time away; the first accepted correct guess has t=0.

## Storage and sharing

Games, preferences and challenge-identified outcomes are stored locally in versioned browser storage. Statistics show wins, losses, the six win buckets and the cumulative score; they are not an online ranking. When a schedule replacement withdraws the activation-day challenge, its outcome is removed and statistics are derived from the remaining games; the replacement's eventual outcome is counted once. Clearing site data, private browsing, unavailable storage, or switching browser/device can lose or isolate progress. The local clock and stored results are trusted and are not tamper-proof. If storage is unavailable, persistence and daily enforcement cannot be guaranteed.

Result sharing uses a dedicated Canvas image without answer or guess letters. Spoiler-free sharing also conceals the first row's feedback. The Statistics dialog keeps its share control in a fixed footer and the manual-copy text in its scrollable content. Native file sharing is capability-detected; where unavailable the text fallback uses clipboard or manual copy. Cancellation does not trigger copying or an automatic download. A replaced challenge withdraws its local presentation, but cannot revoke a share or copy already handed off externally.

The sharing unit tests inspect Canvas drawing commands and text, and exercise capability detection, cancellation, errors and clipboard fallback. The Playwright interface tests cover preparation retry; `e2e/share-window.spec.ts` also decodes the PNG passed to a simulated native share and checks its pixels, user activation and the manual-copy layout. These browser simulations do not establish native share-panel behavior or delivery on a real device. A supporting physical device was not available for verification.

## GitHub Pages

Install the [GitHub CLI](https://cli.github.com/) and authenticate an authorized account with `gh auth login`; confirm with `gh auth status`. For a new installation, ensure the project is not an unexpected existing checkout and the account has no repository with the same name. Initialize `main`, commit the project and lockfile, and use `gh repo create ParoleCompetitive --public --source=. --remote=origin` without overwriting an existing repository. Configure the repository's Pages build source as GitHub Actions, for example with `gh api --method POST repos/OWNER/ParoleCompetitive/pages -f build_type=workflow` when Pages is not yet enabled. Replace OWNER with the authenticated account; a name collision or missing permission requires resolution, not a fabricated remote.

Pull requests run installation, type checking, tests, production build and browser smoke without publishing or access to the daily secret. Main pushes, an authorized manual dispatch on main and the scheduled request publish through the official Pages actions and `github-pages` environment. They serialize the entire publication path without cancelling a running publisher; GitHub may replace pending runs, so neither FIFO nor delivery is guaranteed. Each publisher selects the latest main revision after obtaining its slot, fixes or reuses the current Rome record, verifies and builds that revision, then checks main and the Rome date again before deployment. A changed revision, date, incompatible fixed record or failure stops promotion and leaves the last successful deployment live. No automatic retry or backfill is performed.

The schedule requests 00:07 `Europe/Rome`, not guaranteed midnight availability. GitHub may delay or drop scheduled runs; schedules run only on the default branch and public-repository schedules may be disabled after 60 days of inactivity. See GitHub's [workflow schedule syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onschedule) and [schedule event limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). After a delay or failed deployment, dispatch the workflow manually on main; an already fixed same-day record is reused exactly, even without the key. A missed day is not invented later.

Provision `PAROLE_DAILY_HMAC_KEY` only in the authorized implementation, after checking that the repository secret does not already exist: `gh secret list`. With authorized repository access, generate 32 cryptographically random bytes and supply their 64 hexadecimal digits through protected standard input, for example `openssl rand -hex 32 | gh secret set PAROLE_DAILY_HMAC_KEY`. Never print, commit, pass as an argument, or regenerate an existing key. The generator alone receives it, not dependency installation, tests, build, browser smoke, pull requests, logs, artifacts or client code. If the key is lost, do not silently replace it: existing records remain recoverable without it, while new assignments must wait for authorized provisioning. Rotate only with an explicitly agreed prospective boundary; preserve every fixed record and use the new key solely for unfixed days after that boundary. Repeated requests for an already fixed day reuse its record regardless of the key.

The `daily-data` branch is append-only durable data, not executable workflow input; never rewrite an existing record or resolve an incompatibility by deleting it. Vocabulary changes require an agreed later boundary and compatible clients. The public `daily/current.json` under the configured Pages prefix reveals today's answer, and branch history can reveal prior records; the secret protects future selections, not the current answer. Daily selections can repeat, and no anti-cheat guarantee is made. Old clients cannot follow the new publication protocol. Publication delays leave compatible clients waiting, and an acquired current-day record is the only offline challenge. Inspect the workflow run and Pages settings for the actual deployment URL and status.
